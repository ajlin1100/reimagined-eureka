ServiceNow Application Platform
Initial Team Charter

Mission Statement:
To provide a secure, scalable, and resilient ServiceNow platform that drives organizational efficiency.

By transitioning to a tiered operational structure, the Application Platform Team will ensure rapid fulfillment of routine requests while protecting the architecture required for long-term strategic development.

1. Team Structure & Responsibilities

Platform operations are divided into three distinct tiers to ensure appropriate access levels, protect production data, and optimize resource allocation.

2. Governance & Security Boundary

  • Least Privilege Access: The admin role in the Production environment is strictly reserved for Tier 3 personnel. Tier 1 and Tier 2 staff will receive targeted roles (e.g., knowledge_admin, catalog_admin) and rely on automated workflows to execute production changes safely.
  • Architecture Standard: All new custom departmental applications will be built as Scoped Applications to protect the Global namespace, isolate data, and prevent collisions with baseline ITSM functionality.

Standard Operating Procedure for
Platform Governance & Release Management

1. Request Intake & Triage

  • Centralized Intake: Plan to deprecate direct messaging and emails for platform work. All requests, enhancements, and bug reports will be routed through the designated ServiceNow Platform Request catalog item.
  • Triage Routing: Tier 1 monitors the intake queues (INC, RITM, CHG), resolving standard access/knowledge requests and escalating configuration/architecture requirements to Tiers 2 and 3.

2. The 4-Instance Deployment Pipeline

Direct configuration in the Production environment is strictly prohibited. All configuration and development must traverse the approved instance pipeline to prevent instance drift and ensure thorough testing.

  • Dev: All code and configuration originate here.
  • Test: The mandatory validation gate. Update Sets are fetched and previewed here to catch dependency errors before reaching Production.
  • Prod: Locked runtime environment. Receives committed Update Sets exclusively during approved release windows.
  • Build: Isolated sandbox utilized for Tier 1 and Tier 2 training and experimentation.

3. Update Set Management

  • Adoption: Begin use of Update Sets to manage Dev to Test and Prod deployments.
  • Naming Convention: All Update Sets must follow the standard nomenclature: [App/Module] - [Task/Story #] - [Brief Description] (e.g., ITSM - ENHC00123 - Add Subcategory to Incident).
  • Batching: Complex deployments requiring multiple Update Sets will utilize the Update Set Batching feature. A single Parent Set will be used to move and commit all Child Sets simultaneously.
  • Preview Discipline: 100% of preview errors (e.g., missing fields, scope conflicts) identified in Test or Prod must be resolved or explicitly documented before a commit is executed.

4. Release Windows

  • Releases to Production will occur on a scheduled, recurring basis to bundle changes into predictable deployment packages.
  • Emergency breaks/fixes are exempt from the scheduled window. It is advised to still follow the Dev → Test → Prod pipeline whenever possible to maintain consistency and prevent configuration drift. If deviations are necessary, they must be vetted by the next senior developer, documented and reviewed post-implementation.

5. Instance Maintenance & Cloning

To maintain environmental parity and prevent Update Set preview errors, instances will be cloned using a Milestone-Based Schedule. Clones from Prod to Dev/Test will occur immediately following major application deployments.

Pre-Clone Backup Protocol (30 Minutes Prior)

  1. Export all In Progress or locally Complete Update Sets to XML.
  2. Commit all active Scoped Application changes to the Application Repository or Git source control.
  3. Validate that Data Preservers (for sub-prod properties) and Exclude Tables (for logs/attachments) are active.

Post-Clone Restoration Protocol (30 Minutes Post)

  1. Re-import saved Update Set XMLs into Dev via Retrieved Update Sets.
  2. Revert imported Update Sets to In Progress to resume development.
  3. Pull the latest Scoped Application branches from the repository.
